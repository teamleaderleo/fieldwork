## In simple words

The old Tantivy `prepare_commit()` generation-fence defect is still present on current public `main`, but an open public pull request now proposes a different worker architecture that overlaps the repair.

That pull request removes the old "join one worker, start one replacement, then join the next" mechanism. It does **not** obviously restore the stronger failure guarantee Fieldwork already selected: a failed `prepare_commit()` should not return while another old-generation worker can still publish.

On the current proposal head, `prepare_commit()` returns immediately from the first failed flush acknowledgement. Remaining flush receivers are dropped at that point. A failed persistent worker kills new admission through the existing writer-status bomb, but another old-epoch worker can still be finishing work against the live `SegmentUpdater`.

An exact owned-fork discriminator is prepared against the public proposal head. Execution is queued, so this receipt keeps the overlap finding at `source-read + target-test-prepared`. The narrow repair direction is also source-read only: consume every current-epoch flush, preserve the first error, and return it only after the whole old epoch has settled.

The previously executed old-architecture repair should stay on hold until this overlap gate resolves. A direct-source materialization scaffold for that repair also had a small harness failure; the harness is repaired and queued, but a successful materialization would remain historical/current-main evidence rather than a reason to ignore the live architectural overlap.

## What PR 2999 changes

The proposal makes indexing workers persistent across commits.

Each worker receives an `EpochTask` containing the operation receiver, a flush acknowledgement sender, and a delete cursor. `prepare_commit()` swaps in a fresh operation channel, causing the current epoch to drain. Workers acknowledge that drain and then park for the next epoch instead of exiting and being replaced.

This removes the old partial-replacement sequence. No replacement worker is started after each successful old-worker join because the workers themselves persist.

The proposal also keeps one `IndexWriterStatus` identity across commits. Persistent workers hold bombs tied to that status. If a worker's indexing epoch returns an error, it sends that error through its flush channel and exits without defusing its bomb; dropping the bomb kills the writer status and removes the operation receiver.

That is an important improvement for the old failure shape: after a real worker error, new document admission should be dead.

## The remaining terminal-settlement gap

The proposed `prepare_commit()` flush barrier is currently:

```rust
for flushed in std::mem::take(&mut self.worker_flushes) {
    flushed
        .recv()
        .map_err(|_| TantivyError::SystemError(WORKER_FLUSH_FAILED.to_string()))??;
}
```

The double `?` returns from `prepare_commit()` on the first disconnected flush sender or the first worker error.

Because the vector was moved into the loop, returning there drops all remaining flush receivers. A later worker can therefore still be draining the just-closed old epoch when the caller has already received an error.

The worker-error bomb solves **new admission**. It does not kill `SegmentUpdater`. The worker indexing path owns a clone of `SegmentUpdater`, and `index_documents()` can still finalize a real segment and wait for `schedule_add_segment()` while that updater remains alive.

This leaves one half of the previously selected invariant unresolved:

```text
failed prepare visible to caller
    => new admission is dead
    => but every old-epoch publication is not yet proven settled
```

Evidence class: `source-read`.

## Narrow repair direction for the persistent-worker architecture

The old repair joined all old workers before starting any replacements and then rolled back/rebuilt or failed closed. PR 2999 changes which pieces remain necessary.

A smaller persistent-worker candidate is:

1. move all current `worker_flushes` out as today;
2. receive every one;
3. retain the first worker or disconnect error as the primary error;
4. log later errors without replacing the primary error;
5. after all current-epoch receivers settle, return the primary error if one exists;
6. if any error exists, skip next-epoch task handoff entirely;
7. only when every current-epoch flush succeeds, hand the parked workers the new receiver and install the next set of flush acknowledgements.

Why this is enough for the selected invariant, if the exact discriminator confirms the source model:

- the failed worker's bomb already kills admission;
- successful remaining workers finish the old epoch and park;
- waiting all flushes removes late old-epoch publication authority before return;
- no next epoch is handed out after an error;
- `rollback()` or writer drop already closes epoch channels and joins the parked workers.

This repair direction is `source-read` only. It is not a promoted candidate until target execution proves the missing settlement property on the exact proposal head.

## Adjacent lead: delete-all can preserve stale uncommitted deletes

Review discussion on public PR 2999 produced a separate, pre-existing reproduction from the PR author.

The reported sequence is:

```text
commit a document with term T
queue one or more uncommitted deletes for T
delete_all_documents()  // removes segments and rewinds the stamper
commit the clear
add a new document with T
commit again
```

The author reported that the new document can disappear because the uncommitted delete operations survive the stamper rewind and later overlap the reused opstamp range. They stated the reproduction fails on both PR 2999's parent and proposal branch.

Current August 11 public main still has this `delete_all_documents()` shape:

```rust
self.segment_updater.remove_all_segments();
self.stamper.revert(self.committed_opstamp);
Ok(self.committed_opstamp)
```

There is no delete-queue reset in that method.

`DeleteQueue` currently stores newly pushed deletes in an internal writer vector. Cursors can cause pending operations to be flushed into linked immutable blocks. The type exposes `cursor()` and `push()` but no reset/clear operation.

Consequence for repair design: clearing only the current writer vector is enough for the review author's delete-only reproduction, but source review has not yet proved it covers every already-issued cursor / already-flushed uncommitted-delete state. Do not collapse this into a one-line fix before a target test distinguishes those cases.

Focused search found no dedicated current public issue or repair PR matching this stale-uncommitted-delete sequence.

Evidence class here:

- public author reproduction: externally reported execution;
- August 11 current-main continuity: `source-read`;
- Fieldwork current-main target execution: absent.

Disposition: **park behind the active P0 convergence work**, retain as a concrete follow-up rather than opening another broad lane while #180/#200 and contribution-unit cleanup are active.

## Adjacent known public issue: committed opstamp remains stale

Public Tantivy issue [#2666](https://redirect.github.com/quickwit-oss/tantivy/issues/2666) is still open. It reports that `IndexWriter::committed_opstamp` is initialized from metadata but never advanced after successful commits, which breaks rollback / delete-all stamper rewinds and can reuse opstamps.

Current source still supports that diagnosis:

- repository code search finds no assignment updating `IndexWriter::committed_opstamp` after commit;
- `PreparedCommit::commit_future()` still delegates directly to `SegmentUpdater::schedule_commit()` and returns that future;
- `IndexWriter::rollback()` and `delete_all_documents()` still use the field.

This is distinct from the stale-uncommitted-delete queue problem. Fixing #2666 would make the rewind target accurate; it would not by itself remove delete operations that were queued after the committed point and survive the rewind.

Disposition: existing public owner; avoid duplicate public reporting. No Fieldwork-specific execution was added in this audit.
