## Strongest supported finding

OpenTelemetry JS lifecycle behavior is governed by several different state owners that currently do not share one uniform contract. Useful repairs require keeping those contracts separate:

1. helper startup must be one-attempt and coordinated with shutdown;
2. failed synchronous setup must preserve the primary error while best-effort cleanup remains observable;
3. provider and reader shutdown should expose one authoritative operation and result where the package contract supports it;
4. public telemetry admission should close when provider shutdown begins;
5. teardown-only internal work, such as a periodic reader's final collection, needs explicit narrow authority;
6. every child owned at lifecycle-operation start must be attempted even if an earlier child throws synchronously;
7. delayed same-owner lifecycle recursion can make a shared terminal promise depend on itself;
8. provider shutdown is not installation disposal and cannot safely remove process globals without ownership-aware primitives.

## Failed hypotheses and negative results

- No ordinary Node AsyncLocalStorage propagation defect was found for descendants created under active context.
- A shared consumer created earlier does not automatically acquire a later operation's context; explicit handoff is required.
- Core OpenTelemetry cannot infer one logical retry from separate concrete requests.
- Logger proxy behavior disproved the initial concern that existing logger references are permanently stuck on a no-op provider after first registration.
- Cached metrics recording after shutdown is observable but remains a specification ambiguity for previously returned objects.
- Direct transport retry ordering does not prove the complete exporter sends after its shutdown promise resolves.
- A one-shot metrics reader state change alone was unsafe because it blocked the reader's own final collection.
- `try/catch` alone is insufficient for attempt-all fanout when the iterated child collection is mutable.
- Shared promise identity alone cannot distinguish legitimate concurrency from delayed same-owner callback ancestry.

## Alternative architectures

- one-start-attempt guard versus a full explicit helper state machine;
- synchronous function helper versus an async setup API that can await rollback;
- prevalidation, two-phase reservation, or rollback for metric-reader binding;
- one-shot terminal shutdown versus retryable failed shutdown;
- first-caller operation timeout versus caller-local waiting timeout;
- shared public result plus internal physical-cleanup receipt;
- explicit lifecycle provenance/capability versus contract-only prohibition of same-owner recursion;
- provider shutdown plus separate installation disposer versus one combined teardown method;
- per-signal fanout repairs versus one monorepo invariant with separate package review units.

## Remaining uncertainty

- whether spans created before trace shutdown should still deliver `onEnd` during or after processor shutdown;
- whether trace delayed reentry should remain contract-only or receive runtime protection;
- how metrics records late physical cleanup success or failure after the public result timed out;
- whether failed reader shutdown is permanently terminal in the desired compatibility contract;
- whether cached meters and instruments should stop recording after shutdown;
- which transaction mechanism best repairs partially bound metric readers;
- how installation ownership and compare-and-remove global disposal should be represented;
- whether the attempt-all opening snapshot should be per-provider call or part of a shared helper;
