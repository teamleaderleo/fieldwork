### Candidate design

Owned source PR `teamleaderleo/uv#12` recognizes:

1. exact existing file `uv.lock`;
2. an existing `<script-name>.lock` only when the sibling `<script-name>` currently parses as a PEP 723 script;
3. no other `.lock` file.

It changes only the explicit requirements path. Constraints and overrides keep their current behavior. It does not inspect lockfile bytes or guess from TOML keys.

This is materially better than the public content-sniffing attempts because it derives identity from uv's own naming rule and the producer's script contract.

### Remaining review limits

1. **Non-UTF-8 script names.** The candidate converts the full lock filename through `OsStr::to_str`. On Unix, uv's generator can construct a script lock name with `OsString`, but the detector returns false for a non-UTF-8 filename. This is source-read only and needs a Unix-native test before any acceptance.
2. **Changed or malformed sibling.** A genuine script lock is no longer recognized if the sibling script later loses or corrupts its PEP 723 block. That is a conservative false negative rather than a false positive, but the intended diagnostic contract should be explicit.
3. **Active public overlap.** The open public attempt and repeated prior attempts make independent submission inappropriate without a new public-state check and human maintainer communication.
4. **Current exact-head execution.** Run `30753915919` must complete and be classified before the internal candidate can be accepted even as research.

## Review 2: BusyBox relocatable launchers

### Public problem and overlap

Public issue `astral-sh/uv#16209` documents `realpath: --: No such file or directory` in Alpine/BusyBox-generated launchers. It remains open, unassigned, and labeled bug/compatibility/great-writeup. ### Design comparison

A generation-host BusyBox branch is not obviously correct for relocatable output. A launcher or virtual environment can be generated under one shell/tool implementation and executed after movement under another. Encoding the generator host's `/bin/sh` flavour would therefore make artifact behavior depend on where it was produced instead of remaining portable at execution.

The current candidate instead uses one execution-portable form:

- retain `dirname --`, which the BusyBox control accepts;
- remove only `realpath --`, which BusyBox treats as a missing path and returns nonzero for;
- execute absolute, relative, PATH, spaces, leading-hyphen, and symlink forms on all three platform families.

This supports the global portable form over generation-time introspection, but it remains an inference until the exact source receipt and human upstream design discussion are reconciled.

### Why this is the leading first-contribution candidate

Compared with the other owned uv work, this lane has:

It is still not ready merely because it is small. The final source commit must be inspected independently, the queued run must pass, current public main and duplicate state must be refreshed, and a human must choose how to frame the issue discussion's global-versus-BusyBox-specific design concern.
