## In simple words

Yjs receives binary updates that describe changes made by another copy of a document. A damaged update can report an error after Yjs has already changed the receiving document.

That matters because application code often treats a thrown function call as an all-or-nothing failure. Here, “it threw” and “it changed state” can both be true.

The first executed comparison found this on released Yjs 13.6.31. The current focused carrier determines exactly what changed, which observers ran, whether the partial state can be saved, and whether retrying the complete update repairs the document.

## Why we care

A sync, persistence, or quarantine layer may use an exception to decide that an update was rejected. If the destination already advanced, the layer can:

- persist state it believes is unchanged;
- retry under the wrong assumptions;
- emit duplicate or misleading observer effects;
- acknowledge or quarantine the wrong update boundary;
- compare state vectors that no longer represent the pre-call state.

No durable-data loss has been established. The executed consequence is a recovery-contract ambiguity with observable in-memory state mutation.

## What happens if we leave it alone

Observed: for one 45-byte Yjs update, nine truncated prefixes threw after producing the same visible text as the complete update and advancing the destination state vector.

Inferred: callers that require failure atomicity need an isolation, clone, validation, or retry contract instead of assuming the thrown call rolled back.

Unknown: real-world exposure, observer side effects, persistence behavior, update V2 behavior, current 14.x behavior, and whether official documentation promises atomicity.

## Governing goals and invariant

Governing invariant: a caller must be able to determine whether a failed update changed authoritative document state and how to recover safely.

| Goal or contract | Primary source | Consequence for the design |
| --- | --- | --- |
| Idempotent update delivery | Yjs update APIs and existing update tests at the exact release | A complete retry should be safe if it is the recommended recovery path |
| Causal update integration | `src/utils/encoding.js` at the exact release | Missing dependencies may be retained as pending state rather than rejected atomically |
| Transaction cleanup | `src/utils/Transaction.js` at the exact release | Exceptions can still run observer and cleanup machinery |
| Application-owned persistence | Yjs separates document updates from providers and storage | The application must know whether a thrown apply changed what it may persist or acknowledge |

## Current finding

At released Yjs 13.6.31, `applyUpdate()` is not failure-atomic for every truncated byte prefix.

The initial corpus generated a document containing `abcdef`, deleted `cd`, and encoded the resulting 45-byte full update. Applying cuts 36 through 44 to a fresh document:

- threw `Unexpected end of array`;
- left visible text `abef`, the same value as the complete update;
- changed the encoded state vector from the empty-document value.

The Automerge comparison rejected all 127 truncated prefixes of its second change without mutating the destination object.

This comparison does not by itself make Yjs behavior defective. The open question is whether Yjs documents this as a streaming/non-atomic API contract and whether a complete retry, clone-before-apply, validation pass, or provider-level transaction is the correct recovery boundary.

## System and ownership map

- `applyUpdate()` / `applyUpdateV2()` are the binary update entrypoints.
- The decoder reads client structs and a delete set.
- `integrateStructs()` mutates the document store as decodable structs become available.
- `transact()` owns transaction setup, cleanup, and observer dispatch.
- Providers and persistence adapters decide when bytes are trusted, acknowledged, retried, or durably stored.
- The focused Fieldwork carrier owns fixed inputs, exact package versions, mutation snapshots, observer counts, persistence round-trips, and retry controls.

## Alternatives instantiated or analyzed

### Option A — Document non-atomic application and require caller isolation

- Artifact or branch: paper-only until exact behavior is classified.
- Invariant implemented: authoritative state is changed only after applying untrusted bytes to an isolated clone or staging document.
- Expected benefit: clear recovery even if core integration remains streaming.
- Expected cost or failure: cloning or staging can add memory and latency.
- Discriminating control: persistence and observer effects on a staged versus authoritative document.
- Rollback boundary: discard the staging document.

### Option B — Prevalidate the complete update before integration

- Artifact or branch: paper-only.
- Invariant implemented: malformed bytes are rejected before mutating the document.
- Expected benefit: intuitive failure atomicity.
- Expected cost or failure: duplicate decoding, resource amplification, or inability to validate causal semantics without integration.
- Discriminating control: source prototype and adversarial size measurements.
- Rollback boundary: retain current streaming path.

### Option C — Core transactional rollback after decode failure

- Artifact or branch: paper-only.
- Invariant implemented: a thrown update restores the exact pre-call store and suppresses committed observer effects.
- Expected benefit: direct all-or-nothing API.
- Expected cost or failure: complex rollback across structs, delete sets, pending state, observers, and GC.
- Discriminating control: minimized source candidate plus complete mutation/observer matrix.
- Rollback boundary: revert source candidate.

### Option D — Retry the complete update after any truncation error

- Artifact or branch: focused execution control.
- Invariant implemented: idempotent complete delivery repairs or completes partially integrated state.
- Expected benefit: simple provider recovery.
- Expected cost or failure: observers or persistence may already have seen the partial call; some partial states may not accept retry cleanly.
- Discriminating control: exact full-retry equivalence and event counts.
- Rollback boundary: isolate or reload from durable state instead.
