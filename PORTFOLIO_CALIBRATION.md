# Portfolio and learning calibration

This file is an optional coordinator aid for deciding how far a technically valid Fieldwork result should be promoted. It is **not** a research hypothesis generator, target-ranking scoreboard, or reason to ignore a real defect.

Fieldwork should still capture consequential findings, negative results, useful mechanisms, and exact evidence even when they will never belong on a resume.

## Canonical career and learning context

When a task explicitly asks whether work is worth scarce review, delivery, portfolio, or learning attention, read the current Scrapbook projections rather than rebuilding that context inside Fieldwork:

- [current engineering state](https://github.com/teamleaderleo/scrapbook/blob/main/work/current-state.md) — moving source-first status;
- [portfolio inventory](https://github.com/teamleaderleo/scrapbook/blob/main/work/portfolio-inventory.md) — evidence retrieval index;
- [resume candidates](https://github.com/teamleaderleo/scrapbook/blob/main/work/resume-candidates.md) — scarce one-page selection and marginal signal;
- [working style](https://github.com/teamleaderleo/scrapbook/blob/main/work/records/working-style.md) — capture/reconciliation, evidence, learning-slope, and attention model;
- [current knowledge handoff](https://github.com/teamleaderleo/scrapbook/blob/main/knowledge/HANDOFF.md) — current learning frontiers when the value of an investigation is partly educational.

Source repositories and exact retained evidence still outrank every projection above.

## Capture is cheaper than prosecution

A finding can be worth preserving without being worth taking through implementation, full CI, independent review, human review, and upstream packaging.

Use a funnel:

```text
notice
→ source-map
→ discriminate
→ retain what survived
→ learn / connect
→ promote only when the next transition earns its cost
```

Do not make a famous target name, a clean one-line fix, or an available upstream path sufficient reason for promotion.

## Promotion questions

Before creating a new review surface or asking for scarce human judgment, ask what additional signal the next transition would create.

Strong reasons include one or more of:

- a new technical axis not already demonstrated well;
- a deeper mechanism or cross-layer ownership boundary that materially strengthens understanding;
- externally legible validation such as substantive maintainer review, adoption, merge, or release;
- a meaningful measured performance, reliability, security, recovery, or compatibility result;
- evidence that plausibly displaces a current role-specific resume candidate rather than duplicating it;
- a reusable discriminator, benchmark, testbed, or operational lesson that improves future work;
- a result that closes an important uncertainty in the current Knowledge frontier.

Weak reasons by themselves include:

- another logo;
- another small correctness fix in a mechanism already represented several times;
- CI becoming available;
- a patch already being easy to write;
- sunk effort;
- the possibility of adding one more item to a review desk.

## Review-capacity rule

`REVIEWING.md` remains authoritative: when review debt grows faster than dispositions, consolidate, finish, stop, or archive before adding more review surfaces.

A technically sound result may therefore end as a finding, experiment, scout branch candidate, negative result, or source-reviewed repair direction with no human-review card. That is a successful disposition when further promotion has low marginal value.

## Research independence

Do not read the resume candidate list and then manufacture hypotheses tailored to it.

The correct order is:

1. investigate the assigned system from source and contracts;
2. let discriminators eliminate weak explanations;
3. preserve the result honestly;
4. only then use this calibration when deciding how much additional promotion effort the result deserves.

The portfolio should be a projection of real engineering, not the mechanism that chooses what reality to discover.
