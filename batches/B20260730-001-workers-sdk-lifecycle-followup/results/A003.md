## In simple words

Wrangler can successfully activate new Worker code and then report that deployment failed because a later container or trigger step failed. The current failure path does not consistently print the activated version or name the phase that failed.

## Confirmed mutation order

The deploy helper crosses several mutation boundaries before returning success:

| Phase | Mutation | Can remain applied after a later failure? |
| --- | --- | --- |
| pre-activation | asset sync, Workers Sites sync, resource provisioning, container image build | yes, but Worker code is not yet active |
| activation, versions API | upload version, then create a deployment sending it to 100% traffic | yes |
| activation, legacy API | `PUT` the Worker script | yes |
| post-activation settings | patch tags, tail consumers, logpush, and observability | yes; new-path failure is warning-only |
| post-activation | deploy containers | yes; rejection escapes |
| post-activation | deploy routes, domains, schedules, and other triggers | yes; rejection escapes |

The helper logs `Uploaded` after code activation but before containers and triggers. It logs `Current Version ID` only after trigger deployment succeeds. A trigger failure therefore omits the most useful inspection identifier even though the new code may already be active.

## Package prototype

Added:

- `packages/deploy-helpers/src/deploy/helpers/post-activation-state.test.ts`
- `fieldwork-experiments/deploy-state-reporting/deploy-integration.patch`

The helper reports:

- Worker name;
- activated version ID, or an explicit unavailable marker;
- failed phase: container rollout or trigger deployment;
- warning that the Worker may already be serving new code;
- instruction to inspect current state before retrying or rolling back.

It then rethrows the exact original error. This preserves `APIError` or `UserError` identity, telemetry classification, existing error rendering, and retry behavior.

- Current source already performs an early Docker check specifically to avoid one known disjoint state where Worker code updates and container deployment later fails.

The failure class is therefore established. The fresh contribution is a bounded, testable post-activation state receipt rather than a claim that partial deployment itself is newly discovered.

## Why automatic rollback is not the first repair

A generic rollback is unsafe because:

- trigger deployment may have partially applied routes or schedules;
- container rollout may be independently retryable;
- rollback creates another deployment and can fail;
- the previous code version may not match prior non-versioned settings or triggers;
- a client retry may race an automatic rollback;
- legacy uploads may not expose a reliable version identifier.

The first repair should state what is known and what must be inspected, not claim the deployment was atomic.

## Remaining test surfaces

1. Versions API: container callback rejects after `createDeployment()`.
2. Versions API: trigger deployment rejects after activation.
3. Legacy script `PUT`: trigger deployment rejects after activation.
4. Success emits no receipt.
5. Original error identity remains unchanged.
6. Null or malformed version identifiers are reported as unavailable, never invented.
7. Receipt output appears before the original error is rendered.
8. Existing machine-readable or JSON output modes receive a stable equivalent record rather than terminal-only prose.
