## In simple words

Wrangler can successfully activate new Worker code and then report that deployment failed because a later container or trigger step failed. The current failure path does not consistently print the activated version, identify the activation path, or name the phase that failed.

## Confirmed mutation order

The deploy helper crosses several mutation boundaries before returning success:

| Phase | Applicable path | Mutation | Can remain applied after a later failure? |
| --- | --- | --- | --- |
| pre-activation | both | asset sync, Workers Sites sync, resource provisioning, container image build | yes, but Worker code is not yet active |
| activation | versions API | upload version, then create a deployment sending it to 100% traffic | yes |
| activation | legacy API | `PUT` the Worker script | yes |
| post-activation settings | versions API | patch tags, tail consumers, logpush, and observability | yes; failure is warning-only |
| post-activation | legacy container path | deploy containers | yes; rejection escapes |
| post-activation | both | deploy routes, domains, schedules, and other triggers | yes; rejection escapes |

Important correction from the deeper review: container workers are explicitly excluded from the versions/deployments path at the pinned source revision. Container rollout failure therefore follows a legacy script upload. Trigger failure can follow either activation path.

The helper logs `Uploaded` after code activation but before containers and triggers. It logs `Current Version ID` only after trigger deployment succeeds. A trigger failure therefore omits the most useful inspection identifier even though the new code may already be active.

The helper reports:

- Worker name;
- activation method: versions deployment or legacy script upload;
- activated version ID, or an explicit unavailable marker;
- failed phase: container rollout or trigger deployment;
- warning that the Worker may already be serving new code;
- warning that the failed phase may also have partially applied;
- instruction to inspect current state before retrying or rolling back.

It then rethrows the exact original error. This preserves `APIError` or `UserError` identity, telemetry classification, existing error rendering, and retry behavior.

### Review correction: reporting must be secondary

A review identified that the first helper version called `report(...)` without a guard. A throwing logger or output callback could therefore replace the authoritative deployment error.

The fork now wraps receipt reporting in its own `try`/`catch`, treats reporting as best-effort, and always rethrows the exact original deployment error. Both the dependency-free model and the prepared package test include a regression where `report` throws and require the original error to survive.

## Why the receipt is needed

A command exit code answers only whether the whole workflow completed. It does not answer which irreversible or externally visible mutations already succeeded.

Without the receipt, an operator may incorrectly assume nothing changed, retry blindly, or roll back the wrong state. The required minimum is the same principle used by systems that retain state after partial apply: record observed changes, identify the failed phase, and let retry or rollback be a deliberate next operation.

## Prior discussion and precedent

- The [route-attachment failure after a successful Worker upload](https://redirect.github.com/cloudflare/workers-sdk/issues/1585) left the command failed while the Worker code was deployed.
- The [container-related failure after a Worker script update](https://redirect.github.com/cloudflare/workers-sdk/issues/12483) documented the same broad partial-apply class, although that report may also involve invalid registry configuration.
- Current source already performs an early Docker check specifically to avoid one known disjoint state where Worker code updates and container deployment later fails.
- Terraform records successful resource changes in state when apply later errors and explicitly does not attempt generic automatic rollback.
- AWS CloudFormation exposes preservation, retry, update, and rollback as distinct failure policies rather than assuming rollback is always correct.
- Kubernetes separates desired state from observed status and uses typed conditions, reasons, messages, and observed generations to make partial or stale state inspectable.

The failure class is established. The fresh contribution is a bounded, testable post-activation state receipt rather than a claim that partial deployment itself is newly discovered.

## Options

### Leave behavior unchanged

No compatibility risk, but a failed command can conceal active new code and partially applied later phases. Recovery remains guesswork.

### Move every check before activation

Useful where possible and already done for Docker availability, but impossible for failures that occur only while mutating remote routes, schedules, containers, or settings.

### Automatically roll back on any later failure

Simple mental model when rollback is reliable, but unsafe here because resources have different rollback semantics, some later phases may partially apply, the legacy path differs from versions deployment, and rollback itself is another mutation that can fail.

### Make the whole deployment transactional server-side

Best atomicity, but requires a broader Cloudflare API contract spanning code, containers, routes, domains, schedules, and settings. Wrangler alone cannot manufacture that transaction.

### Emit a post-activation receipt and preserve the original error

Recommended first step. It improves recovery without changing API semantics, retries, or rollback behavior. Receipt reporting itself must remain best-effort and secondary.

### Add idempotent phase retries later

Potential follow-up, but each phase needs a stable operation identity and proof that replay cannot duplicate or widen effects.

## Why automatic rollback is not the first repair

A generic rollback is unsafe because:

- trigger deployment may have partially applied routes or schedules;
- container rollout may be independently retryable;
- rollback creates another deployment and can fail;
- the previous code version may not match prior non-versioned settings or triggers;
- a client retry may race an automatic rollback;
- legacy uploads may not expose the same version identity and rollback guarantees as the versions path.

The first repair should state what is known and what must be inspected, not claim the deployment was atomic.
