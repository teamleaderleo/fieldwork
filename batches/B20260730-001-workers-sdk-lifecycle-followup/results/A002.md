## In simple words

Wrangler and the Cloudflare Vite plugin can start from the same directory and choose different Wrangler configuration files. The difference is not limited to one extension: they use different extension order, different directory-search boundaries, and different generated-config redirect behavior.

## Strongest finding

The source trace distinguishes different selection policies:

- Workers Utils, used by Wrangler, searches upward once per extension in the order `wrangler.json`, `wrangler.jsonc`, then `wrangler.toml`.
- The Vite plugin checks only the configured Vite root in the order `wrangler.jsonc`, `wrangler.json`, then `wrangler.toml`.
- Wrangler callers may opt into `.wrangler/deploy/config.json` and select a generated deployment configuration.
- Vite resolves a concrete source configuration path and passes it explicitly into Wrangler's config reader, which bypasses redirect discovery.

These policies are individually coherent, but their combined effect is not exposed as one inspectable contract.

## Precedent review

Added:

`fieldwork-experiments/config-selection-contract/precedent-and-policy.md`

Primary comparison set: TypeScript, Prettier, ESLint, Vite, Biome, Cargo, and recent Workers SDK redirect changes.

### Common patterns

- Automatic discovery and an explicit path are separate modes. Explicit paths win.
- The search anchor is part of the contract: target file, current directory, script directory, or project root.
- Most single-config tools choose the nearest directory first and use filename priority only to break a same-directory tie.
- Project-root tools such as Vite deliberately avoid inheriting configuration from unrelated ancestors.
- Complex discovery needs an inspector, trace, or clearly documented merge order.

### Cloudflare-specific evidence

Merged upstream PR `cloudflare/workers-sdk#14897` added generated-config redirect support specifically to `wrangler triggers deploy`, matching other deployment commands. This confirms that generated configuration is established behavior and that redirect adoption is currently distributed across command-specific flags.

### Unusual current behavior

Workers Utils performs a full upward search for JSON before trying JSONC or TOML. A farther parent JSON can therefore beat a nearer child JSONC or TOML. That is existing compatibility behavior, but it differs from the nearest-first model users commonly encounter.

## Classification

### Intentional or defensible

The Vite plugin's root-only boundary is defensible because Vite owns an explicit project root and should not necessarily inherit a configuration from an unrelated parent workspace.

An explicit `configPath` taking precedence is also a useful escape hatch and matches broad tool precedent.

### Compatibility-sensitive

The opposite JSON/JSONC precedence can change bindings, entry points, environments, and deployment settings without changing the invocation directory.

Workers Utils' format-first upward search is surprising but source-confirmed. It should not be silently changed.

### Insufficiently explicit

Redirect behavior is enabled command-by-command rather than represented as a shared policy. A selected-path string does not report rejected candidates, search boundary, selection reason, or source-versus-generated relationship.

## Options

### Leave behavior unchanged

Lowest compatibility risk, but preserves silent divergence and command-specific drift.

### Force Vite onto Wrangler discovery

Creates parity but can inherit unrelated parent configuration and violates Vite's project-root model.

### Force Wrangler onto Vite root-only discovery

Creates deterministic root behavior but breaks nested-directory CLI workflows and callers without a known project root.

### Require explicit paths in framework workflows

Deterministic but shifts coordination burden to every framework and does not solve ordinary Wrangler discovery.

### Shared engine with named policy profiles

Recommended. Centralize mechanics and produce a selection trace while allowing `wrangler-cli`, `wrangler-dev`, and `vite-root` profiles to retain compatibility-sensitive defaults.

## Recommended repair direction

Introduce a shared configuration-selection policy and result record with explicit fields for:

- command and invocation profile;
- requested path;
- search starting directory;
- upward-search boundary;
- nearest-first, format-first, or hierarchical-merge mode;
- extension precedence;
- deploy-config redirect enablement;
- user/source config path;
- selected/effective config path;
- deploy-config path;
- environment passed to normalization;
- candidates considered and stable rejection reasons;
- stable selection reason: `explicit`, `root-discovery`, `upward-discovery`, or `deploy-redirect`.

Migration order:

1. characterize current behavior;
2. centralize without changing outcomes;
3. add `config explain` or stable verbose output;
4. warn for ambiguous layouts where named profiles disagree;
5. consider default alignment only through a documented major migration.

## Negative results and limits

- Environment selection changes normalization after a file is selected; it is not another file-discovery policy in the inspected paths.
- Explicit config paths already provide convergence, so a new override mechanism is unnecessary.
- The exact combined divergence matrix was not found as one existing upstream issue.
- The package test is committed and source-reviewed but unexecuted because this environment cannot materialize the full workspace and dependencies.
- The predecessor dependency-free discovery and redirect probes were executed successfully.

## Handoff

The source behavior claim and precedent review support a behavior-preserving protocol refactor. A default-changing implementation should wait for package execution, ambiguity telemetry or compatibility evidence, and a documented migration decision.
