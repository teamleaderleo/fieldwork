## Strongest finding

**Observed in source and reproduced by a controlled model:** a rejection from an awaited cleanup operation before `Runtime.dispose()` exits `Miniflare.dispose()` before the workerd child-kill path runs. `CloudflarePoolWorker.stop()` catches that rejection, writes it through `util.debuglog`, and returns after the remaining pool-level cleanup. This is a sufficient mechanism for a hidden live workerd child after an otherwise successful test result.

**Source-established for unresolved work:** a pre-runtime cleanup promise that never settles keeps `Miniflare.dispose()` suspended before `Runtime.dispose()`. In that case, the Vitest pool never reaches its rejection handler, remote-session disposal, or `poolWorkerStopped()`.

This establishes lifecycle unsafety. It does not establish that the open parallel-file report `cloudflare/workers-sdk#14903` exercises this exact path.

## Source trace

### `Miniflare.dispose()`

At the pinned revision, disposal performs these steps in order:

1. abort the disposal controller;
2. synchronously poison existing proxies;
3. await readiness and the runtime mutex;
4. await browser-process cleanup;
5. remove the exit hook;
6. await proxy-client disposal;
7. await runtime disposal;
8. close runtime and dev-registry dispatchers with local error suppression;
9. await loopback-server shutdown;
10. close live-reload and WebSocket servers;
11. schedule temporary-directory cleanup and handle email-session removal;
12. await inspector-proxy disposal;
13. await dev-registry disposal;
14. await Hyperdrive-proxy disposal;
15. delete the instance from the registry.

The `finally` block guarantees entry into cleanup after readiness failure. It does not guarantee execution of later awaited statements after one cleanup rejects or remains pending.

### Pre-runtime failure points

- `#closeBrowserProcesses()` awaits `Promise.all()` across browser shutdowns. Browser shutdown has explicit graceful-close and exit time bounds. A synchronous process-kill or WebSocket construction failure can still reject the aggregate. This path is bounded under ordinary timer progress.
- `ProxyClient.dispose()` awaits termination of the per-Miniflare synchronous-fetch worker thread. Its `Worker.terminate()` call has no local deadline in this path. A rejection skips runtime disposal; an unresolved termination promise delays it indefinitely.

### Runtime termination

`Runtime.dispose()` clears the process reference, destroys stdin/stdout/stderr and the control pipe, sends `SIGKILL` to the child, and waits for the recorded exit promise. Therefore:

- a failure before this method can leave workerd alive;
- a failure after this method cannot prevent the kill request already being sent;
- a pending runtime exit promise can still hold disposal after the kill request.

### Vitest pool ownership

Each `CloudflarePoolWorker` owns its Miniflare instance. `stop()` closes the socket and awaits `mf.dispose()`. A rejection is caught and logged only through the `vitest-pool-workers` debug channel. The same pattern handles remote-proxy session disposal.

Shared assets watchers use a global active-worker reference count. `poolWorkerStopped()` closes them when the final pool worker stops.

Consequences:

- a rejected Miniflare disposal continues to remote-session disposal and `poolWorkerStopped()`;
- a pending Miniflare disposal blocks both later operations;
- parallel files or projects increase the number of live Miniflare instances and concurrent cleanup paths, while providing no source proof that parallelism itself creates the pre-runtime failure.

### Pre-runtime injection

The first case injects one rejection from `ProxyClient.dispose()` and invokes `Miniflare.dispose()`.

It asserts that the first disposal:

- propagates a disposal error;
- still sends `SIGKILL` to workerd.

On the pinned implementation, the second assertion should fail because the injected proxy rejection occurs before `Runtime.dispose()`. The test restores the injected component and performs a second disposal solely to terminate the child exposed by the failing case, keeping the test runner itself from hanging.

### Post-runtime negative control

The second case injects one rejection from `DevRegistry.dispose()`, which runs after runtime termination. It asserts that the first disposal already sent `SIGKILL`. This separates “cleanup rejected” from “cleanup rejected before runtime ownership was discharged.”

### Why this test is stronger than the retained probe

The retained probe models sequential JavaScript control flow. The package test creates a real Miniflare instance, starts a real workerd process, injects failure through an exported component prototype, and observes the real child-process kill call. It avoids relying on private-field access and cleans up the deliberately exposed child.

## Rejected explanations and negative controls

1. **“The `finally` block guarantees runtime termination.”** Rejected. An awaited rejection inside `finally` exits the block before later statements.
2. **“The Vitest pool catch provides a fallback kill.”** Rejected. It records the error through `util.debuglog`; it contains no child-process termination.
3. **“Any cleanup rejection can skip workerd termination.”** Rejected. Only failures before the runtime step can skip the kill request. The DevRegistry injection is the package-level negative control.
4. **“Remote-proxy session disposal explains the skipped kill.”** Rejected for the rejection mechanism. Remote-session cleanup runs after Miniflare disposal. A pending Miniflare disposal can prevent the session cleanup from starting.
5. **“An assets watcher leak is the direct result of a rejected Miniflare disposal.”** Rejected. The pool catches the rejection and proceeds to `poolWorkerStopped()`. A pending disposal can retain the watcher reference count.
6. **“Open HTTP connections keep workerd alive after `Runtime.dispose()` runs.”** Rejected as the primary mechanism here. Runtime disposal uses `SIGKILL`, specifically avoiding graceful-connection delay. A skipped call, failed kill, or unresolved exit wait remains possible.
7. **“Parallel execution proves a shared-state race.”** Rejected. Parallelism is a credible amplifier and matches #14903, while the traced mechanism is per-Miniflare and requires a pre-runtime cleanup failure or pending promise.
8. **“#14180 and #12764 demonstrate the same defect.”** Rejected. They establish nearby teardown failure classes involving Durable Object rejection/logging and output-gate diagnostics. They do not identify a host-side proxy or browser cleanup rejection before runtime disposal.

## Prior-art assessment

- `cloudflare/workers-sdk#14903`: strongest external match for the user-visible result—passing parallel files, a live workerd child, and a process that never exits. The report lacks a clonable reproduction and reports no debug teardown error, leaving this specific rejection path unconfirmed. A pending operation remains compatible with the absence of a caught error.
- `cloudflare/workers-sdk#14180`: a self-contained Vitest-only teardown hang involving a Durable Object `blockConcurrencyWhile()` callback that logs and rejects. The reported workaround changes promise handling around that runtime operation. This is a credible alternative cause.
- `cloudflare/workers-sdk#12764`: teardown-related `outputGateBroken` log noise with passing tests. It supports the broader presence of runtime teardown edge cases while describing visible stderr noise, not a skipped child kill.
- Historical Miniflare work already moved runtime cleanup into a `finally` after initialization failure. The current gap is finer-grained isolation within that cleanup block.

## Bounded repair direction

1. Treat `Runtime.dispose()` as must-run ownership discharge.
2. Execute independent cleanup components through a tagged settling helper and collect failures instead of allowing the first rejection to skip the rest.
3. Preserve ordering constraints: runtime dispatchers close after runtime termination; loopback and proxy servers close in a controlled phase; instance-registry deletion remains final.
4. Add a deadline diagnostic around pre-runtime operations. On expiry, record the component and continue to runtime termination. A diagnostic should identify the last completed phase and retain the unresolved promise for debug reporting.
5. Throw one `AggregateError` after bounded cleanup completes. `CloudflarePoolWorker.stop()` can preserve the primary test result while emitting one visible secondary warning and full debug details.
6. Add package tests for:
   - rejection before runtime termination;
   - rejection after runtime termination;
   - a controllable pending pre-runtime operation;
   - runtime kill requested before the pending-operation diagnostic deadline;
   - multiple simultaneous Miniflare instances to confirm ownership remains instance-local.

A broad `Promise.allSettled()` over the entire teardown is too coarse because several ordering dependencies are explicit. The repair should use small phases with named components.
