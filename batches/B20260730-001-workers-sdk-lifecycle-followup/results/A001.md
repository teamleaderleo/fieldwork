## In simple words

Miniflare owns a `workerd` child process. Its disposal path awaits browser and proxy cleanup before reaching the runtime method that sends `SIGKILL` to that child.

A rejection from an earlier awaited cleanup can skip the kill request. An earlier promise that never settles can delay it indefinitely. The Vitest pool catches a rejection and continues its remaining pool cleanup, while a pending disposal blocks those later operations as well.

The mechanism and a bounded runtime-first candidate are accepted research results. The real Miniflare package regression remains prepared and unexecuted, so source integration stays gated on exact target execution and leak checks.

## Strongest finding

**Source-read and model-executed:** a rejection from an awaited cleanup operation before `Runtime.dispose()` exits `Miniflare.dispose()` before the synchronous `workerd` kill path runs.

**Source-read and model-executed:** a pre-runtime cleanup promise that never settles keeps disposal suspended before runtime termination. The Vitest pool therefore never reaches remote-session disposal or its final shared-worker bookkeeping for that pool worker.

This is a sufficient lifecycle mechanism for a hidden live child after an otherwise successful test result. It is not established as the exact cause of the [public parallel-files hang report](https://redirect.github.com/cloudflare/workers-sdk/issues/14903).

## Source trace

At the pinned base, `Miniflare.dispose()` enters cleanup after readiness failure and then performs these relevant steps in order:

1. await browser-process cleanup;
2. await proxy-client disposal, including termination of the synchronous-fetch worker thread;
3. await runtime disposal;
4. close runtime and dev-registry dispatchers;
5. continue loopback, WebSocket, inspector, registry, Hyperdrive, and instance cleanup.

A `finally` block guarantees entry into this sequence. It does not make every later awaited statement must-run after an earlier rejection or indefinite wait.

`Runtime.dispose()` clears its process reference, destroys child streams, sends `SIGKILL`, and returns the recorded exit promise. This yields three distinct outcomes:

- a failure before the method can skip the kill request;
- a failure after the method cannot undo the request already sent;
- a pending child-exit promise can still hold disposal after the request.

Each `CloudflarePoolWorker` owns its Miniflare instance. Its `stop()` method catches a rejected Miniflare disposal and logs it through the debug channel, then continues remote-session and shared assets-watcher cleanup. A pending Miniflare disposal blocks those later calls.

## Bounded implementation direction

### First slice — runtime ownership

Start `Runtime.dispose()` before awaiting browser and proxy cleanup. `Runtime.dispose()` sends `SIGKILL` synchronously, so this requests child termination before another cleanup can reject or remain pending. Preserve the rule that runtime exit precedes dispatcher closure.

Validate the first three package cases before and after the candidate. Prove:

- the vulnerable base fails the pre-runtime rejection and pending controls for the intended reason;
- the candidate passes them;
- the post-runtime negative control stays green;
- no child, worker thread, dispatcher, or unhandled rejection leaks from the test.

### Second slice — failure collection

Preserve the primary initialization or operation error while recording secondary cleanup failures. Use small named phases because several cleanup operations have ordering dependencies. Review deadlines and error aggregation separately from the runtime-first ownership patch.

A broad `Promise.allSettled()` over the entire method would erase those dependencies and expand the first repair.

## Rejected explanations and controls

- **The `finally` block guarantees runtime termination.** An awaited rejection inside the block exits before later statements.
- **The Vitest pool catch provides a fallback kill.** It logs the error and contains no child-termination call.
- **Every cleanup rejection can skip the kill.** Only failures before runtime disposal can do so; the post-runtime case is the negative control.
- **Remote-session cleanup causes the skipped kill.** It runs after Miniflare disposal. A pending Miniflare disposal can prevent it from starting.
- **Rejected Miniflare disposal necessarily leaks the shared assets watcher.** The pool catch continues to final worker bookkeeping. A pending disposal can retain that ownership.
- **Parallel execution proves a shared-state race.** It increases concurrent lifecycle paths. The accepted mechanism remains per-Miniflare and requires an earlier rejection or pending operation.
