# Approaches — Unit 02: BusyBox-safe relocatable launchers

## Final selected approach

Remove unsupported `--` delimiters from every generated relocatable launcher owner, preserve `realpath`-before-`dirname` resolution, and make `copy_entrypoint` recognize both the corrected shebang and the historical delimiter-bearing shebang.

Exact final source: `c42973ef0490c75df1c7e7f4e9a54d46c6bca059`.

## Decision criteria

1. BusyBox success should produce clean stderr.
2. GNU and macOS launcher behavior should remain successful.
3. Symlink-first sibling-interpreter selection must remain intact.
4. Wheel, virtualenv, and project-run source must stay synchronized.
5. Existing generated launchers should remain recognizable after uv upgrades.
6. The source branch should remain one reviewable commit with no execution machinery.

## Selected design details

### Generator text

- Wheel relocatable shebang: `realpath "$0"`, then `dirname`.
- POSIX relocatable activation: delimiter-free nested `realpath`/`dirname`.
- Fish relocatable activation: delimiter-free `realpath`/`dirname` calls.

### Project-run recognizer

Two named constants record the exact accepted generated forms:

- `RELOCATABLE_SHEBANG` — corrected form;
- `LEGACY_RELOCATABLE_SHEBANG` — historical form.

`copy_entrypoint` checks the corrected form first, then the historical form, then existing absolute-path forms.

### Regression test

`copy_entrypoint_accepts_current_and_legacy_relocatable_shebangs` runs both exact forms through the private function and verifies:

- new interpreter shebang;
- retained script body;
- retained executable mode.

## Why dual recognition won

Existing virtual environments and installed entrypoints can survive a uv upgrade. Generation changes immediately; old files remain old until regenerated. Recognizing only the corrected form would make `copy_entrypoint` silently skip an earlier uv-generated launcher.

The extra source is localized to the existing recognizer owner and has a direct test. This gives a clean migration path without broad refactoring.

## Viable alternatives considered

### Recognize only the corrected form

Advantages: smallest textual patch and no historical constant.

Reason rejected: it introduces an avoidable migration edge for persisted launchers generated by earlier uv versions. Previous source head `c43b1262be71d9fc0b60ca613700ef7ae60bf69d` had this limitation; the deeper pass repaired it.

### Normalize option-like `$0` in shell

Possible design: wrap `$0` with a shell `case` and prefix `./` when it begins with `-`.

Reason rejected:

- Linux and macOS direct shebang probes show shell `$0` becomes the script pathname even when the caller forces process argv0 to `-tool` or `--help`;
- the supported `./-tool` invocation passes on GNU, BusyBox, and macOS;
- a normalization branch adds generated text and recognizer complexity for a synthetic shell-injection condition.

Reopening trigger: a supported direct launcher invocation that exposes a bare option-like shell `$0`.

### Runtime BusyBox detection

Reason rejected: adds branching to every generated launcher while the delimiter-free candidate already passes GNU, BusyBox, and macOS matrices.

### Redirect utility stderr

Reason rejected: hides genuine resolution failures alongside the BusyBox diagnostic.

### Replace `realpath` with `readlink -f`

Reason rejected: changes the utility and portability contract. Upstream issue #8058 and PR #8079 established symlink-first resolution through `realpath`.

### Centralize all launcher text across crates

Reason deferred: broader dependency/helper design. The current patch centralizes the two accepted project-run forms locally; cross-crate sharing can be discussed separately.

### Move the compatibility test to an integration suite

Still viable as a maintainer preference. The unit test directly reaches the private function and gives exact, cheap coverage. An integration test would exercise more command context at higher cost.
