# Plan

## Phase 1: Define the packet

Use the current upstream packet template and identify the smallest evidence set required for different contribution classes:

- deterministic bug fix;
- runtime or platform compatibility fix;
- type-system regression;
- performance change;
- security-sensitive correction;
- design proposal without implementation.

## Phase 2: Apply to genuine work

Apply the method only when an active project produces a real external-system question. Do not search for artificial test submissions.

For each case, record:

- time spent before contact;
- evidence available at first contact;
- questions asked by maintainers;
- defects found before and after submission;
- revisions requested;
- final outcome;
- reusable artifacts.

## Phase 3: Compare cases

Look for patterns without treating small samples as universal evidence. Distinguish project governance, contributor familiarity, change type, and maintainer availability.

## Phase 4: Revise the method

Remove ceremony that does not improve decisions. Add checks only where a real failure justifies them.

## Safety and ethics

- one intentional interaction at a time per target unless maintainers request otherwise;
- no automated comments, reactions, pings, or submissions;
- no hidden AI authorship where upstream policy requires disclosure;
- no sensitive production evidence;
- no conclusions about reviewer effort that public evidence cannot support.
